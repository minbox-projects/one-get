# Project memory

This file records the current standards and behavior of the OneGet desktop downloader, its task-first React interface, its HTTP, HuggingFace, and video download pipelines, its direct, system, and manual proxy transport, its Netscape-file and captured-browser cookie sources, its signed component catalog and installer, its durable task, HuggingFace, and component stores, and its loopback browser-capture boundary. Agent Notes record why decisions were made; keep both consistent in the same change.

## Platform-layer rule

Target-specific branches belong only in `src-tauri/src/platform/**` and platform-specific Tauri configuration. Shared modules call platform interfaces and never branch on the target operating system. New platform behavior needs an interface in the platform layer plus a test in the corresponding suite.

## Download engine and task store

- Entry points: `Engine` in `src-tauri/src/engine/scheduler.rs` (`new`, `add_task`, `add_task_with_cookies`, `run`, `pause`, `resume`, `cancel`, `retry`, `recover`, `delete_record`, `delete_file`, `open_file`, `open_folder`, `set_max_concurrent`, `set_proxy`, `set_network_options`, `set_huggingface_options`, `set_cookie_file`, `set_task_rate_limit`, `set_global_rate_limit`, `set_logger`), `EngineService` in `src-tauri/src/engine/service.rs`, `Database` in `src-tauri/src/store/db.rs`, `HfMetadataStore` in `src-tauri/src/store/hf.rs`, and `DownloadSpec` in `src-tauri/src/engine/worker.rs`.
- Engine service: one dedicated thread with a current-thread Tokio runtime owns the engine and store. Requests arrive through a channel and the run loop is polled concurrently with them; slow probes run alongside both loops so a pending probe does not stall task listings or controls. Startup recovery completes before `start` returns; paused-task revalidation is guarded to run once per engine instance rather than on every run-loop restart; and `shutdown` pauses active downloads and refuses later work. `settings_save` applies the maximum concurrent tasks and global rate limit to the live engine.
- Task filenames and destinations: `Engine::add_task` runs the platform-aware sanitizer for the current target before the name reaches the store or the in-memory spec. The sanitizer never returns an empty or dot-segment name, so task creation cannot persist a traversal or separator component. The resolved destination is validated, stored with the task, and reused for the part and final file after restart; a stored task without a destination falls back to the configured default, and an invalid destination fails with a typed `INVALID_DESTINATION` error. The post-redirect URL is stored in the same minimized form as the task URL and exposed as `finalUrl` in list summaries and details.
- Deletion and opening: `delete_record` accepts only completed, failed, or cancelled tasks and removes only the task's own part while keeping a final file. `delete_file` accepts only completed tasks, removes the capability-validated final file and then the record, and returns `FILE_MISSING` while keeping the record when the final file is absent. `open_file` requires a completed task and an existing final file; `open_folder` uses the recorded destination; both use the shell-free platform opener.
- Part-file operations: the engine resolves the task's persisted `part_path` and falls back to the legacy `<sanitized filename>.oneget.part` name only when none was recorded. Part existence and removal go through `CapDir::exists` and `CapDir::remove_file`, which apply the same path validation, canonical-root check, and symbolic-link refusal as every other managed operation. A missing part is not an error on cancel, and a part that resolves outside the destination root is never touched.
- SQLite schema version 3: `schema_meta`, `tasks`, and `segments`; version 2 adds nullable `destination`, `completed_at_ms`, and `final_url`, and version 3 adds `kind` (`http` or `video`) and nullable `video_json`, with every version-2 row migrated to `http` in the same transaction. Version-1 rows keep a null destination and final URL until they are resolved or recorded. WAL, `synchronous=NORMAL`, foreign keys, a five-second busy timeout, and `0600` on the database plus `-wal` and `-shm` on Unix. Back up a non-empty database before a migration, migrate in one transaction, verify indexes and constraints, and refuse a newer schema. Timestamps are epoch milliseconds; offsets are signed 64-bit columns whose non-negative range preserves `u64`.
- Task states: `queued`, `connecting`, `downloading`, `paused`, `finalizing`, `completed`, `failed`, `cancelled`. Segment states: `pending`, `active`, `done`, `failed`. Only the checked transitions persist; anything else returns `INVALID_STATE`. `completed` requires a final file and matching stored hash; `paused` and `failed` preserve the part; `cancelled` removes only its own part. A video task has no segment rows and keeps its progress, stage, output, and completion in `video_json`.
- Queue: FIFO claim of the oldest queued `http` task; video tasks are claimed only by the video service. The HTTP concurrency limit counts only `connecting`, `downloading`, and `finalizing`; a paused task does not consume a slot; a limit change takes effect without a restart. An HTTP control, retry, or finalization that reaches a `video` task returns `TASK_KIND_UNSUPPORTED` before changing state.
- Cross-engine coordination: more than one `Engine` may open the same database. A pause or cancel applied through one instance is reconciled from the reloaded stored row by the other, so a concurrent pause ends `paused` and a concurrent cancel ends `cancelled` instead of `failed` or `INVALID_STATE`. A cancel that wins during finalization removes the part and leaves no final file, and a finalizing replacement that loses to a cancel removes the file it created.
- Data truth: the chosen part file is the byte truth and SQLite segment rows are the progress truth. A task normally uses `<sanitized filename>.oneget.part` beside its destination; only when a same-filename task in the effective destination conflicts does the engine choose `<sanitized filename>.<first 8 of task id>.oneget.part`. Conflict detection compares the effective destination, so a version-1 row without a stored destination falls back to the engine default directory, and it includes any same-filename task that is not completed or cancelled plus terminal rows whose part file still exists. The part-name choice and task insert share one `BEGIN IMMEDIATE` transaction, so two engine instances cannot race for the same name. The chosen name is persisted in `part_path` and is the single part identity for download, resume, finalize, cancel, recovery, delete, and existence checks, with the legacy name as fallback. A known total is preallocated sparsely through `PartFile::preallocate` and `CapDir::preallocate_sparse`, an unknown total starts empty, and writes use absolute `u64` offsets. A preallocation failure on a full device maps to `DISK_FULL` and pauses the task; other preallocation failures fail it. Progress persists at least once per 128 KiB read chunk.
- Finalization: stop workers, sync the part, stream SHA-256, persist the computed hash before the rename, verify an expected hash case-insensitively, choose a unique `stem (n).ext` name on collision, replace through `CapDir` without overwriting or following links, and sync the parent directory. A checksum mismatch fails with `CHECKSUM_MISMATCH` and creates no final file. A cancel from another engine instance that lands during finalization stays authoritative: the part is removed and no final file is left behind.
- Recovery: interrupted `connecting` or `downloading` tasks requeue when the part exists and fail with `PART_MISSING` otherwise; `finalizing` tasks re-finalize idempotently; a final-only file must match its stored hash, or, without one, the recorded total plus any expected hash; a cancelled leftover part is removed; paused and failed parts stay.
- Probe and Range: one ranged `GET` with `Range: bytes=0-0` and `Accept-Encoding: identity`; classify 206, 200, 416, HTML, and HTTP errors without reading the body. HTTP/1.1 only, no automatic redirects, ten manual hops, configurable connect and read timeouts with defaults of 15 and 30 seconds, no compression, and no public-network dependency. A probe is independent of the run loop, so a slow probe never stalls downloads or list and control requests. Revalidate the first range before the pool; a 200 with no bytes written falls back to one connection, and a 200 after bytes exist fails with `RANGE_IGNORED` without writing.
- Planning and splitting: 1 to 64 connections, half-open gap-free segments, 1 MiB minimum except the whole file or final remainder, and one open-ended segment for unknown length or no Range. A segment may split at most twice, only with an idle worker, at least two minimum segments remaining, and a split point ahead of the current offset; persist the shortened range and its tail in one transaction.
- Retry and faults: a configurable 1 to 10 attempts, default five, with exponential backoff and full jitter between 50 milliseconds and two seconds. Integer-seconds `Retry-After` is honored exactly; an HTTP-date or malformed value uses the exponential fallback. Do not retry 401, 403, 404, HTML, checksum, or a Range-ignored failure after data. A short body resumes at the persisted offset, an overlong body is truncated at the segment end, an invalid Content-Range start is `RANGE_MISMATCH` without writing, and ENOSPC pauses with `DISK_FULL`.
- Rate limiting: a byte leaky bucket paces each streamed chunk. Per-task and optional global limits share the schedule across a task's workers; zero or absent is unlimited. Rate-limit inputs are capped at `Number.MAX_SAFE_INTEGER`, the largest value the IPC number boundary carries without rounding.
- Proxy: `proxyMode` is `direct` (default), `system`, or `manual`. Manual uses `proxyType` `http`, `https`, or `socks5`, a non-empty host, a port 1 to 65535, and optional basic username and password from the operating-system credential store; the proxy URL never embeds userinfo. System mode reads the macOS `scutil --proxy` or Windows Internet Settings values, prefers the HTTPS endpoint then HTTP, never carries credentials, and connects directly with a stable reason when PAC, WPAD, or unreadable configuration prevents discovery. The effective proxy applies to the HTTP engine, video service, and component downloader; stored credentials are used only in manual mode and are deleted when direct or system mode is saved.
- Cookies: one source per task, never merged. A per-task or default Netscape cookie file wins, then captured browser cookies. Cookie files match host, include-subdomains, path, secure, and expiry, are reloaded at task start or resume, and are recomputed per redirect hop. Captured browser cookies are memory-only, at most 100 per item and 8 KiB combined, URL-scoped at capture and use, single-use through an opaque handle, and never persisted; an unknown or consumed handle fails with `INVALID_COOKIE_HANDLE`, a scope mismatch with `COOKIE_SCOPE`, and an over-limit list with `COOKIE_LIMIT`. Reject `Host`, `Authorization`, `Cookie`, `Range`, `Proxy-Authorization`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Upgrade`, `TE`, `Trailer`, and `Set-Cookie` custom headers, and reject CR or LF in names or values.
- HuggingFace: recognize `huggingface.co`, `www.huggingface.co`, `hf.co`, and `www.hf.co` model, `/datasets/`, and `/spaces/` file URLs under `/resolve/` or `/blob/`, normalize `/blob/` to `/resolve/`, and reject other resolver paths with `HF_NOT_A_FILE`; CDN and unrelated hosts stay ordinary and never receive the token. The initial resolution may retry once after a 401, and that retry is not a signature refresh; it follows at most ten resolver redirects and returns `HF_AUTH` when authorization still fails. After a successful initial resolution, a CDN 403 may trigger up to three signature refreshes, so a fully exercised task contacts the resolver at most four times; each refresh avoids re-downloading completed bytes, the refresh count starts at 0 and reaches 3 at the limit, a rejected refresh after the limit is `HF_SIGNATURE`, and a refresh that reports unauthorized is `HF_AUTH`. The stored token is sent only to resolver hosts. A 429 or an ignored Range reduces the task to one connection for the rest of the run. `hfConnectionCap` (1 to 64, default 8) caps effective connections and is captured at task start. `hf.db` schema version 1 stores task id, repository, file path, revision, connection cap, effective connections, refresh count, and downgrade state; a missing or corrupt file keeps tasks listable, and a paused HuggingFace task resumes after restart by re-resolving and continuing from persisted offsets.
- User-Agent: a configured non-empty User-Agent without line breaks is the fallback for HTTP and HuggingFace requests that carry no per-task value; per-task headers still win.
- Privacy: header values, cookie values, proxy credentials, authorization values, HuggingFace tokens, and URL query or fragment tokens are never persisted or logged. Safe header names may be stored with empty values; values stay in memory only. The stored task URL and post-redirect final URL strip userinfo, query, and fragment. Logs carry event names, task and segment identifiers, byte counts, and stable error codes only. There is no telemetry or remote reporting.
- Platform: macOS uses sparse `set_len`; Windows attempts `FSCTL_SET_SPARSE` before extending and reports sparse or an explicit fallback. Both use the capability-scoped replace path.
- Harness and soak: `cargo run --bin engine_harness -- run|status|pause|resume|cancel` against a local fixture. The short smoke runs in `cargo test --test soak`; the ignored long run is `ONEGET_SOAK_SECONDS=86400 cargo test --test soak -- --ignored --nocapture` in `src-tauri/` or `bash scripts/soak-test.sh 86400`.

## Components and video pipeline

- Trust root: the build embeds a 32-byte Ed25519 public key as 64 lowercase hexadecimal characters through `ONEGET_COMPONENT_TRUST_PUBLIC_KEY`. A build without it reports `COMPONENT_TRUST_UNCONFIGURED` and disables installs, while an installed component whose recorded target and file hashes verify stays usable. `ONEGET_COMPONENT_MANIFEST_URL` overrides the catalog URL for local fixtures. No private key or seed is stored in the repository or logged.
- Catalog: `src-tauri/src/kernel/` verifies strict Ed25519 over canonical JSON (sorted keys, no whitespace, duplicate keys rejected, top-level `signature` removed, 1 MiB limit) and enforces schema version 1, exactly `yt-dlp`, `ffmpeg`, and `deno`, display version, positive monotonic sequence, license, targets `macos-arm64`, `macos-x64`, and `windows-x64`, role sets (`ffmpeg` requires both `ffmpeg` and `ffprobe`), safe unique output names, HTTPS or test-only loopback URLs, 64-character lowercase SHA-256, positive size, and `binary` or `zip`. A missing current-target artifact is `COMPONENT_UNSUPPORTED`. The raw signed bytes are cached atomically as `catalog.json` and re-verified on every load.
- Install: artifacts are downloaded with redirects disabled and a declared-size bound, then require the exact size and SHA-256. ZIP extraction reads the archive once, validates all members before writing, extracts only declared regular files, and rejects path escapes, links, duplicates, undeclared or missing files, more than 32 entries, more than 256 MiB per file, more than 512 MiB total, or a compression ratio above 200:1. Files are staged in a hidden work directory, prepared for execution (Unix mode, macOS quarantine best effort), renamed atomically to `data/kernel/<component>/<sequence>-<sanitized version>`, and recorded with per-file hashes.
- Component store: `components.db` schema version 1 with `schema_meta` and `component_installs` (component, version, sequence, target, version directory, per-file role/name/SHA-256/size, install time, active). A partial unique index allows one active record per component; activation deactivates the previous record in the same `BEGIN IMMEDIATE` transaction. Update requires a strictly newer sequence; an equal sequence is up to date and a lower one is refused. Rollback verifies and activates an installed earlier sequence with no network request. No automatic pruning; at least one previous version is retained. Deleting the database leaves tasks, files, settings, and pairings untouched.
- Resolver: before any probe or download, active records are checked for current target, version directory, file set, size, and every SHA-256. Failures are `COMPONENT_MISSING`, `COMPONENT_HASH`, `COMPONENT_UNSUPPORTED`, or `COMPONENT_VERSION_MISMATCH`. Status states are `not_installed`, `installed`, `update_available`, `rollback_available`, `tampered`, `unsupported`, and `manifest_unavailable`; operation phase and percent are in-memory.
- Video service: `src-tauri/src/video/service.rs` runs one dedicated thread with a current-thread Tokio runtime, a request channel, control map, and probe path alongside the run loop. It runs one video at a time and persists a later confirmation as `queued`, starting it only after the active task reaches completed, failed, or cancelled. Startup recovery keeps queued and paused tasks, marks interrupted connecting, downloading, or finalizing tasks failed with `VIDEO_INTERRUPTED`, and preserves their temporary directory. Shutdown pauses the active task within the process bound and refuses later work.
- Probe and quality: yt-dlp runs with `--dump-single-json --no-playlist --no-warnings --skip-download --ignore-config`, optionally with the Deno runtime, cookies file, and credential-free HTTP proxy. Live, DRM-only, malformed, and unsupported results are typed failures. The quality model orders video and audio-only choices, estimates video-only merged sizes with the best audio size, marks MP4 compatibility, and defaults to the highest MP4-compatible choice with a highest-available fallback.
- Video execution: yt-dlp receives a fixed allowlist, the machine-readable progress template, `--concurrent-fragments 4`, the active ffmpeg directory, and a task-owned `.oneget-video-<id>` directory under the destination, then merges to MP4 or extracts M4A. The output moves to a unique destination filename and its SHA-256 is stored before completion. Pause preserves the temporary directory; resume adds `--continue`; cancel removes only task-owned data and a finalizing final file; retry reuses preserved data. The full URL stays in memory only, so retry after a restart fails with `VIDEO_URL_UNAVAILABLE`. HLS, DASH, and AES-128 are delegated to yt-dlp and ffmpeg; the application never fetches a manifest, decrypts a segment, or bypasses DRM.
- Process containment: shell-free Unix process group or Windows Job Object, concurrent stdout and stderr draining, combined 2 MiB capture with 8 KiB tails, and a minimal allowlisted environment. Production bounds are 60 seconds for a probe, 30 seconds to first download progress, 120 seconds of inactivity, and 5 seconds to terminate and reap; tests inject shorter values. Typed failures are `VIDEO_TIMEOUT`, `VIDEO_OUTPUT_LIMIT`, `VIDEO_PROCESS_FAILED`, `VIDEO_SPAWN_FAILED`, `VIDEO_MERGE_FAILED`, and `VIDEO_INTERRUPTED`. A yt-dlp report that no supported JavaScript runtime exists becomes `VIDEO_JS_RUNTIME_MISSING`, which offers the Deno component install entry. Finalization fails as `VIDEO_OUTPUT_MISSING` when the task-owned directory holds no single non-empty output, `VIDEO_OUTPUT_MOVE_FAILED` when the move into the destination fails, or `VIDEO_OUTPUT_HASH_FAILED` when the SHA-256 cannot be streamed; a hash failure removes the moved final file.
- Cookies and proxy: a per-video cookies file must exist, its contents are never read, and a per-video HTTP or HTTPS proxy rejects userinfo. A per-video proxy overrides the effective settings proxy for that probe or download; otherwise the configured proxy applies. Values are passed only to yt-dlp and are not persisted in logs.

## Browser integration and capture protocol

- The loopback API binds `127.0.0.1:37652` synchronously before serving on a dedicated current-thread Tokio thread. It is optional: a bind or pairing-database failure leaves downloads and settings usable and reports browser integration unavailable with the stable reason code of the failure, including `PAIRING_UNAVAILABLE` when no pairing store is attached, `API_BIND_FAILED` when the port cannot be bound, and `PAIRING_SCHEMA_UNSUPPORTED` when the pairing schema is newer than this build. Shut the API down before the engine on quit.
- Routes are `GET /health`, `POST /pair`, `POST /capture`, and `POST /pair/revoke`. Admission order is the request-header budget, exact loopback `Host`, route origin, JSON content type for the two body routes, bearer authentication for capture and revoke, then the route rate limit and body validation. `/health` allows an absent `Origin`, rejects a present non-extension origin, and returns app version, protocol version 2, and capture, prefill, and takeover capabilities without authentication. The desktop accepts protocol versions 1 and 2; an older desktop rejects version 2 with `PROTOCOL_MISMATCH`.
- Limits: 64 KiB body, 50 capture items, 8 KiB URL, 255 UTF-8 bytes for a filename, 10 safe capture headers with 128-byte names and 2048-byte values, 64 request headers and 16 KiB combined header bytes, 10 pairing requests per origin per minute, 120 capture requests per token per minute, and 256 retained keys per limiter. Rejections use typed `{ code, message }` bodies and create no task or prefill.
- Pairing codes are eight digits with a ten-minute lifetime, one active code at a time, superseded by a new code and discarded when the app reopens. A token is 256 random bits as 64 lowercase hexadecimal characters and is returned exactly once. `pairing.db` stores only SHA-256 hashes of codes and tokens plus the exact browser-extension origin (Chromium `chrome-extension://` or Firefox `moz-extension://`), label, and timestamps, with schema version 1, WAL, `synchronous=NORMAL`, a five-second busy timeout, and `0600` on Unix. Five failed codes lock pairing for five minutes; authorization requires the exact bound origin; last-used updates are throttled to once per minute; revocation deletes the client.
- Capture intents are `takeover` and `prefill`. A takeover carries exactly one item, creates one task, and returns the existing task with `duplicate: true` for a repeated token-bound `sourceId`. A prefill carries one or more items, stores one in-memory pending list, emits `app://capture-prefill`, and creates no task. Only the safe headers `Referer`, `User-Agent`, `Accept`, and `Accept-Language` are accepted; authorization values, arbitrary headers, credentialed URLs, and kinds other than `file` are rejected. Protocol version 2 items may carry an optional cookie list from the extension's default-off opt-in: at most 100 cookies and 8 KiB combined, each scoped to the item URL, rejected as `COOKIE_SCOPE` or `COOKIE_LIMIT` and never persisted; version 1 items carry none.
- Prefill delivery uses the event plus a fetch-on-open command. One item opens New Download with URL, filename, and a `Referer` header; multiple items open Batch Download with their URLs. A busy dialog defers the prefill until it closes, a second prefill replaces the pending one, dismissing the dialog drops it, and no prefill survives an app restart.
- Both extension packages are MV3 with `cookies`, `webRequest`, `downloads`, `storage`, `tabs`, and `webNavigation`, host permissions for HTTP(S) pages and loopback, and `script-src 'self'`. The cookie permission is used only when the default-off `sendCookies` setting is enabled; the shared controller then attaches only cookies scoped to the captured URL to takeover and prefill requests and never stores their values. Chromium runs a service worker and retains `downloads.onDeterminingFilename`; Firefox runs a `background.scripts` event page with Gecko ID `oneget@oneget.app`, `strict_min_version` 140.0, and `data_collection_permissions.required: ["none"]`, and has no `onDeterminingFilename`. The isolated content script owns the overlay and forwards metadata; a MAIN-world script observes fetch, XHR, media elements, and SPA navigation without extension APIs. The token and settings live in the browser's local storage area; bounded resource metadata lives only in the session storage area.
- Resource categories are `video`, `audio`, `archive`, `program`, `document`, `model`, and `other`, derived from the lowercased filename extension first and MIME type second. HLS is `.m3u8` or an HLS manifest MIME; DASH is `.mpd` or `application/dash+xml`. Manifests are listed but never takeover candidates and are never fetched for parsing. `.ts`, `.m4s`, `.m4f`, `.cmfv`, `.cmfa`, `init.mp4`, and `videoplayback` range, sequence, or fragment URLs are filtered.
- Takeover reads the current token and settings per decision, checks enablement, category, blacklist host and subdomain, incognito, extension-originated, non-HTTP, manifest, unsupported kind, and known size, and exempts unknown sizes from the minimum-size rule. Chromium decides in `downloads.onDeterminingFilename` and still calls `suggest()`; Firefox decides in `downloads.onCreated`, reduces an absolute filename to a sanitized basename with a URL-derived fallback, treats `totalBytes: -1` as unknown, and can miss a download that finishes before cancellation. It sends the capture before canceling and erasing the browser download; a failed capture leaves the download intact and records `takeoverError { downloadId, url, filename, reason }` for `popup/get-state`, where the popup shows a localized banner with a Send to OneGet prefill retry. Chromium keeps that record in memory; Firefox keeps the same bounded record in session storage so an event-page suspension does not lose the retry path. Reasons are `token_revoked` after a 401 clears the token, `update_required` after a 409, and `capture_failed` otherwise; it is never written to persistent storage and clears after a successful takeover or same-URL prefill retry. The per-tab store keeps at most 500 entries per tab and 50 tabs, clears the sending frame on a frame navigation or a subframe SPA route change, the whole tab on a top-frame tab navigation or SPA route change, and the tab on close.



## Command and event contract

- Commands: `app_info`, `settings_get`, `settings_status`, `settings_save`, `hf_token_status`, `hf_token_save`, `hf_token_clear`, `proxy_credentials_status`, `proxy_credentials_save`, `proxy_credentials_clear`, `deep_link_last`, `diagnostics_secret_roundtrip`, `diagnostics_notification_status`, `diagnostics_send_notification`, `diagnostics_autostart_get`, `diagnostics_autostart_set`, `app_graceful_quit`, `downloads_list`, `downloads_segments`, `downloads_probe`, `downloads_add`, `downloads_pause`, `downloads_resume`, `downloads_cancel`, `downloads_retry`, `downloads_delete_record`, `downloads_delete_file`, `downloads_open_file`, `downloads_open_folder`, `video_probe`, `video_start`, `kernel_status`, `kernel_manifest_refresh`, `kernel_install`, `kernel_update`, `kernel_rollback`, `pairing_status`, `pairing_generate_code`, `pairing_list_clients`, `pairing_revoke`, and `pairing_take_pending_prefill`.
- `settings_status` reports whether the loaded document is read-only because of a future schema and whether corrupt input was recovered; it never returns the document content.
- Events: `app://deep-link` with `{ accepted, url?, error? }` and `app://capture-prefill` with `{ items, receivedAtMs }`.
- Pairing commands never return a bearer token: status and client views carry only identifiers, origins, labels, and timestamps. `pairing_take_pending_prefill` takes the one pending prefill exactly once.
- `downloads_list` summaries expose `kind`, an optional video summary, an optional HuggingFace summary (`repoId`, `filePath`, `revision`, `effectiveConnections`, `refreshCount`, `downgraded`), and the active `cookieSource` (`file` or `browser`) with `cookieCount`; task details expose the minimized post-redirect target as `finalUrl`. Control, delete, open, and retry commands route by task kind, and `downloads_segments` is empty for a video task.
- Rust payloads use camelCase and typed `{ code, message }` errors. A missing engine reports `engine_unavailable`.
- The frontend calls only `src/lib/tauri.ts` or the typed wrappers in `src/lib/downloads.ts`, `src/lib/video.ts`, `src/lib/kernel.ts`, and `src/lib/pairing.ts`; components never invoke Tauri directly. A missing Tauri runtime yields `runtime_unavailable`; the shell must not crash in a browser preview.
- Blocking keyring, file, settings, and download work runs through `spawn_blocking` or the engine service thread; no command blocks the UI thread.
- Polling: the UI calls `downloads_list` at most once per second while the window is visible, pauses while it is hidden, and refreshes after a control action or mutation. Do not add a per-task progress event stream.
- Quitting: `app_graceful_quit`, the close behavior, and the tray path shut the engine service down before exit; do not start a second engine over the same task database.

## Desktop interface

- The main window is task-first: sidebar state and type filters with counts, a toolbar with New, Batch, Pause All, Resume All, search, and Settings, a central task list, a collapsible details panel, and a status bar with active-task and total-speed information. The empty state explains how to add a download. `src/features/diagnostics/DiagnosticsPanel.tsx` remains a retained, tested module, but the task-first shell does not mount it. The `Toast` primitive is mounted for localized success feedback.
- The task list virtualizes fixed-height rows with overscan so at most a bounded window of rows is mounted, while sorting, filtering, and search operate on the full data set. The default sort is creation time descending; the state sort uses the fixed order downloading, connecting, finalizing, paused, queued, failed, completed, cancelled with creation time as the tiebreaker.
- The list and rows are kind-aware: an HTTP row shows byte progress and segments, while a video row shows its video stage and opens a video details section with title, duration, uploader, quality, and final file without invented segments. Video controls use the same state-aware enablement and localized errors, and a missing or tampered component error shows a direct entry to Settings > Components.
- New Download offers Parse video beside URL parsing. The quality dialog shows probed title, duration, uploader, ordered video and audio-only choices with estimated sizes, MP4 compatibility, destination, and filename, and starts exactly one task per confirmation. When "always ask quality" is off, parsing starts exactly one task with the preferred MP4-compatible or highest quality using the form's destination, filename, and connections. Optional per-download cookies-file and HTTP-proxy inputs are validated before creation, and a captured-cookie prefill carries its memory-only cookie handle into the created task.
- Settings mounts Network, HuggingFace, Video, and Extension sections beside General, Download, and Components. Network covers proxy mode and type, host, port, authentication status, default cookies file, global rate limit, connect and read timeouts, retry attempts, and User-Agent; HuggingFace covers token status with save, replace, and clear plus the connection cap; Video covers always-ask and the preferred quality; Extension aggregates pairing availability and states that takeover rules live in the extension popup. Invalid values produce localized field errors and no partial save. Components shows state, active and available versions, installed versions, current target, rollback target, localized errors, install/update/rollback actions, and operation phase and percent. Status polls only while an operation is active and refreshes after each action; settings schema version 2 adds only optional fields.
- Every user-visible string comes from `src/i18n/` in Simplified Chinese or English, follows the operating-system language by default, switches immediately, and persists in settings. Numbers, sizes, speeds, ETA, and dates use locale-aware formatting; components must not hardcode user-facing prose. Stable engine error codes map to dictionary keys through `src/features/downloads/errorMessages.ts`; `CHECKSUM_MISMATCH` tells the user to retry only with the correct expected SHA-256 or without it, and success actions show localized toasts.
- Dialogs trap and restore focus, icon-only actions have accessible names, destructive actions require confirmation, and a keyboard-only user can complete new download, control, details, settings, and record-deletion flows. The task list exposes list and row semantics.
- New and batch dialogs use the localized `@tauri-apps/plugin-dialog` 2.8.4 directory picker. Connection input is a whole number from 1 to 64 within the `u32` range, rate input is a positive whole number at most `Number.MAX_SAFE_INTEGER`, the largest value the IPC number boundary carries without rounding, and an invalid destination surfaces as a destination-specific actionable `INVALID_DESTINATION` error. Segment ranges are half-open, with the end offset exclusive.
- Loading, empty, filtered-empty, retryable error, confirmation, and success states are explicit. A missing runtime or rejected IPC renders a localized non-crashing state with retry guidance and no secret values.
- `e2e/support/mock-ipc.ts` provides deterministic IPC for browser checks; Playwright flows must not depend on a public network or a real credential.

## Security invariants

- No analytics, telemetry, remote script sources, or remote connect sources. The production CSP is bundled-only except IPC; keep the no-telemetry rule when adding any network behavior.
- Deep links accept only `oneget://download` with exactly one `url` parameter, an `http` or `https` target, no embedded credentials, valid percent encoding, and at most 8 KiB.
- Credential values live only in the operating-system credential store. Never write them to settings, logs, diagnostics payloads, or frontend state; diagnostics return booleans only. Values are redacted in formatting and zeroized on drop.
- Managed file access goes through `CapDir` under a canonical root. Reject absolute paths, parent or current components, NUL bytes, and symbolic-link or junction escapes; atomic replace refuses link sources and destinations.
- Sanitize user-supplied filenames with the platform-aware sanitizer before use.
- Component catalogs use canonical JSON with sorted keys and no whitespace, reject duplicate keys and input above 1 MiB, remove the top-level signature before hashing, and use `verify_strict` with a build-time public key. Installation additionally requires schema, component, sequence, role, name, archive, size, hash, and URL policy to pass; without the trust key installs are disabled but verified installed components stay usable. An artifact is never extracted or executed before its exact size and SHA-256 verify.
- Guarded child processes never use a shell; they run in a Unix process group or Windows Job Object with whole-tree kill and timeout, drain both pipes concurrently, and cap combined output. The shell-free platform opener is the intentional exception: it launches the operating-system handler detached and fire-and-forget with no process guard, because a guard would kill the handler the application must leave running.
- The main window hides on close by default and can be configured to quit instead; the tray provides Show and Quit; graceful quit shuts down the engine, records a shutdown event, and exits with code 0.
- The engine store is the progress authority and the part file is the byte authority. Never write a full `200` body at a nonzero offset, never produce a partially written final file, and never mark a task completed without a matching stored hash.
- Record deletion never removes a completed final file, and file deletion is allowed only for a completed task after a second confirmation; the engine validates the final file through the capability root before removing it and its record.
- The platform opener runs without a shell, launches the operating-system handler detached without a process group or Job Object, and refuses to launch a path that does not exist or a non-completed task.
- The engine rejects non-`http`, non-`https`, and non-`socks5` proxy schemes, credentialed targets, HTTPS-to-HTTP redirects, URLs over 8 KiB, forbidden headers, and CRLF-bearing header values before a request. A HuggingFace resolver URL is recognized only on the four canonical hosts, and the token is attached only to resolver-host requests. The video pipeline accepts only validated HTTP(S) page URLs and runs only the hash-verified installed tools.
- Cookie values, captured browser cookies, proxy credentials, HuggingFace tokens, authorization values, URL query tokens, and custom header values never enter the SQLite stores or the structured log. The task store keeps only necessary recovery fields; `hf.db` keeps repository, file, revision, connection, refresh, and downgrade metadata only.
- The local API binds only `127.0.0.1`, requires the exact loopback `Host` on every route and the exact paired browser-extension origin on every write — `chrome-extension://` with 32 `a`–`p` characters or `moz-extension://` with a lowercase 8-4-4-4-12 UUID — reads bearer tokens only from the `Authorization` header, and returns no wildcard CORS. The accepted scheme changes no admission order, limit, token binding, or error code, and it enforces body, item, URL, header, protocol, and rate limits before creating a task or prefill.
- `pairing.db` stores only SHA-256 hashes of single-use codes and bearer tokens plus the exact bound browser-extension origin, label, and timestamps. Never return a token from a desktop command, log it, write it to settings, or render it in the UI.
- Capture accepts only URL, filename, referer, MIME type, size, file kind, the four safe headers, and a protocol version 2 cookie list that must be URL-scoped and within the 100-cookie and 8 KiB bounds. Reject authorization values, arbitrary headers, credentialed URLs, unsupported kinds, out-of-scope cookies, and over-limit lists before the engine or dialog sees them; prefill content and captured cookies stay in memory and are never persisted.
- Both extension packages use bundled-only MV3 scripts with no remote code or eval, no native messaging, and no telemetry; the Firefox package also declares no data collection. The `cookies` permission is used only for the default-off opt-in that attaches URL-scoped cookies to a capture, and the MAIN-world observer never reads response bodies, cookies, or credentials. Resource metadata stays session-only and bounded.
- Takeover posts the capture before canceling or erasing the browser download, creates at most one task per token-bound source, and leaves the browser download intact on failure. It attaches cookies only when the user enabled the opt-in. The failure surface is memory-only on Chromium and session-storage bounded on Firefox so an event-page suspension keeps the localized popup retry, and it is never written to persistent storage.
- Component ZIP extraction validates every member before writing, extracts only declared regular files, and rejects path escapes, links, duplicates, undeclared or missing files, and entry, size, or compression-ratio limit violations with no extracted output. Component execution requires re-verifying the active target, version directory, file set, sizes, and per-file hashes.
- A video cookies file and per-video proxy are per-download inputs passed only to yt-dlp; a per-video proxy overrides the effective settings proxy, and the configured proxy applies otherwise. Cookie contents are never read, proxy userinfo is rejected, and neither value is persisted or logged. The application never parses HLS or DASH manifests, decrypts segments, or bypasses DRM.
- The video service runs one task at a time, confines its temporary directory to the destination, removes only task-owned data on cancel, and requires a moved output plus stored SHA-256 before completion. A failed or interrupted task leaves no partial final file.

## Settings, logging, and errors

- Settings use `schemaVersion: 2` with `theme` (`system`, `light`, `dark`), `logLevel` (`error`, `warn`, `info`, `debug`, `trace`), `language` (`system`, `zh-CN`, `en-US`), `closeBehavior` (`tray`, `quit`), optional `defaultDirectory`, `defaultConnections` (8), `maxConcurrentTasks` (3), optional `globalRateLimit` in bytes per second, and these optional fields with defaults: `proxyMode` (`direct`, `system`, `manual`), `proxyType` (`http`, `https`, `socks5`), `proxyHost`, `proxyPort`, `defaultCookiesFile`, `userAgent`, `connectTimeoutSecs` (15, range 5 to 120), `readTimeoutSecs` (30, range 5 to 300), `retryAttempts` (5, range 1 to 10), `hfConnectionCap` (8, range 1 to 64), `alwaysAskQuality` (true), and `videoQualityPreference` (`mp4Compatible`, `highest`). A version-1 document migrates in memory without losing theme, log level, or unknown fields. Preserve unknown top-level fields, save atomically through a same-directory temporary file and rename, back up corrupt documents to a `.corrupt` sibling, treat a future schema as read-only, validate all fields before saving with no partial save, and never write proxy credentials or the HuggingFace token to the document. Language and theme apply immediately; default directory and connections apply to new downloads; concurrency and the global rate limit apply to new tasks after saving while running downloads keep their captured limits, and the UI states this; close behavior applies immediately; effective proxy, timeout, retry, User-Agent, cookie, and HuggingFace options apply to tasks that start or continue after the save. Manual proxy mode requires a non-empty host and a port 1 to 65535.
- Logs are JSON lines with `timestamp`, `level`, `event`, and redacted `fields`. Redact credential-bearing URL parts, authorization and cookie headers, URL userinfo, proxy credential fields, and provider credential prefixes before serialization.
- Rotation defaults to 10 MiB per file and five files including the current file; a record is never split across files. Debug builds also write the redacted line to stderr.
- Errors are user-safe typed `AppError` values with stable codes and no internal paths, stack traces, or credential values. `EngineError` follows the same rule and carries an internal retryability flag and optional retry delay.
- The task database is not a settings store. It holds minimized task URLs, filenames, per-task destinations, states, offsets, remote metadata, hashes, error codes, connection counts, timestamps, and safe header names with empty values.
- The pairing database is a separate `pairing.db`, not part of the task store. Deleting it revokes every paired client and affects no task, completed file, or setting. HuggingFace metadata uses a separate `hf.db` at schema version 1; deleting it loses HuggingFace details and affects no task, completed file, or setting. The settings schema stays version 2, the task-store schema is version 3, and components use `components.db` at version 1. Proxy credentials and the HuggingFace token live only in the operating-system credential store, not in settings.
