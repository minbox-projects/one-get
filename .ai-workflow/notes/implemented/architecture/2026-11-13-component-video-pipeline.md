# Agent Note: Signed components and the video pipeline

Status: implemented

English | [中文](2026-11-13-component-video-pipeline.zh.md)

## Problem

OneGet could download HTTP files but could not procure trustworthy media tools or download a video. A desktop video chain needs yt-dlp and ffmpeg on macOS and Windows, an optional JavaScript runtime for some sites, a way to know that those binaries are the ones a maintainer intended, and a task model that does not disturb the existing HTTP engine. Without recorded decisions, later work could trust an unsigned catalog, run a downloaded executable before verifying it, mix video tasks into HTTP claims and recovery, run several videos behind one progress model, leave partial output on cancel or failure, or persist cookies and proxy credentials that the existing privacy boundary forbids.

## Decision

The component trust root is an Ed25519 public key configured when the application is built, supplied as `ONEGET_COMPONENT_TRUST_PUBLIC_KEY`. The private key never enters the repository, the runtime configuration, or a log. A build without the key reports `COMPONENT_TRUST_UNCONFIGURED` and disables installation, but an already installed component whose recorded target and file hashes verify remains usable. `ONEGET_COMPONENT_MANIFEST_URL` is a runtime override for local fixtures. The signed catalog is strict canonical JSON verified with `verify_strict`, schema version 1, exactly the components `yt-dlp`, `ffmpeg`, and `deno`, and per-target artifacts for `macos-arm64`, `macos-x64`, and `windows-x64`. Each component declares a display version, a positive monotonic sequence, a license, and per-target URL, SHA-256, size, archive type, and file roles; `ffmpeg` owns both the `ffmpeg` and `ffprobe` roles. A catalog that omits the current target is unsupported and never falls back to another platform. Verified bytes are cached atomically as `catalog.json` and re-verified on every load. The maintainer tool `kernel_manifest` implements `keygen`, `sign`, and `verify`, and `scripts/kernel-fixture.mjs` prepares a local signed setup without writing key material inside the repository.

Installation records live in a separate `components.db` at schema version 1 with one active record per component. An artifact is downloaded with a declared-size bound and accepted only after its exact size and SHA-256 match. ZIP extraction reads the archive once, validates every member before writing, and extracts only declared regular files, rejecting path escapes, links, duplicates, undeclared or missing files, more than 32 entries, more than 256 MiB per file, more than 512 MiB total, and a compression ratio above 200:1. Files are staged in a hidden work directory, prepared for execution, renamed atomically to `data/kernel/<component>/<sequence>-<sanitized version>`, and recorded with per-file hashes. Update activates only a strictly newer sequence; rollback verifies and activates an installed earlier sequence without a network request. The resolver re-verifies target, version directory, file set, size, and every hash before execution and refuses a missing, tampered, unsupported, or inconsistent record. No automatic pruning runs, and deleting the database leaves tasks, files, settings, and pairings untouched.

The task store moves to schema version 3 with a `kind` of `http` or `video` and a nullable structured `video_json`; every version-2 row becomes an `http` task in the migration transaction. HTTP claims, active and queued counts, recovery, paused revalidation, and part-conflict detection remain HTTP-only, and an HTTP control, retry, or finalization that reaches a video task returns `TASK_KIND_UNSUPPORTED`. A video record carries its progress, stage, output, and completion without byte segments, so `downloads_segments` is empty for a video task.

The video service runs on one dedicated thread with a current-thread runtime, a request channel, a control map, and a probe path alongside the run loop. It runs one video at a time; a later confirmation is persisted as `queued` and starts only after the active task reaches completed, failed, or cancelled. Startup recovery keeps queued and paused tasks, marks interrupted connecting, downloading, or finalizing tasks failed with `VIDEO_INTERRUPTED`, and preserves their task-owned temporary directory. Shutdown pauses the active task within the process bound and refuses later work. yt-dlp runs with a fixed argument allowlist, a machine-readable progress template, `--concurrent-fragments 4`, the active ffmpeg directory, and `.oneget-video-<id>` under the destination, then merges to MP4 or extracts M4A. The output moves to a unique destination filename and its SHA-256 is stored before completion. Pause preserves the temporary directory, resume adds `--continue`, cancel removes only task-owned data and a finalizing final file, and retry reuses preserved data. The full source URL stays in memory only, so a retry after restart fails with `VIDEO_URL_UNAVAILABLE` instead of reusing the minimized stored URL.

Every video child is shell-free, runs in a Unix process group or Windows Job Object, drains stdout and stderr concurrently, captures a combined 2 MiB with 8 KiB tails, and uses a minimal allowlisted environment. The production bounds are 60 seconds for a probe, 30 seconds to the first download progress line, 120 seconds of inactivity, and 5 seconds to terminate and reap; tests inject shorter values. Failures are typed as `VIDEO_TIMEOUT`, `VIDEO_OUTPUT_LIMIT`, `VIDEO_PROCESS_FAILED`, `VIDEO_SPAWN_FAILED`, `VIDEO_MERGE_FAILED`, `VIDEO_OUTPUT_MISSING`, or `VIDEO_INTERRUPTED`. A per-video cookies file and a per-video proxy are the video inputs passed only to yt-dlp; the per-video proxy overrides the effective settings proxy for that probe or download, and the configured proxy applies otherwise. Cookie contents are never read, proxy userinfo is rejected, and neither value is persisted or logged. HLS, DASH, and AES-128 transport is delegated to the installed tools, and the application never fetches a manifest, decrypts a segment, or bypasses DRM.

The interface adds a Components section with component state, active and available versions, installed versions, target, rollback target, operation phase and percent, localized errors, and install, update, and rollback actions; a missing-component error opens it. New Download offers Parse video and a quality dialog with video and audio-only choices, estimated sizes, destination, filename, and optional per-download cookies and proxy, and starts exactly one task per confirmation. Video details show title, duration, uploader, quality, merge stage, and final file without invented segments. The new commands are `video_probe`, `video_start`, `kernel_status`, `kernel_manifest_refresh`, `kernel_install`, `kernel_update`, and `kernel_rollback`; `downloads_list` gains `kind` and a video summary, controls route by kind, and `downloads_segments` stays empty for video.

This decision extends the [OneGet desktop shell baseline](2026-11-11-oneget-desktop-shell-baseline.md), the [Download engine and durable task store](2026-11-12-download-engine-task-store.md), and the [Desktop download interface and engine service](2026-11-13-desktop-download-ui.md); those records are partially superseded where their kernel boundary, task schema, and task surface are stated. The [Local browser API and pairing boundary](2026-11-13-local-api-browser-capture.md) and the [Firefox extension parity](2026-11-13-firefox-extension-parity.md) records keep their unchanged browser boundary. The later [HuggingFace downloads, network transport, and cookie sources](2026-11-15-huggingface-network-capabilities.md) record partially supersedes this record's per-download-only proxy and cookie statement by adding a global proxy and opt-in browser-cookie capture for HTTP while video cookies stay per-download and a per-video proxy overrides the configured one; this record stays active for the component, video, HLS, process, and task-kind decisions.

## Alternatives considered

- Trusting a manifest that is fetched over TLS without a separate signature was declined because the catalog controls executable downloads; a compromised host or asset would otherwise become code execution.
- Reading the trust key from settings or a first-run prompt was declined because it would make the trust root mutable at runtime and would let a local configuration change authorize different binaries.
- Downloading and executing the newest upstream tool on demand was declined because it provides no pinned version, size, or hash and makes a later probe depend on an unverified network response.
- Storing component records in the task database was declined because component lifetime and rollback are independent of tasks; a separate database can be deleted without touching task, file, settings, or pairing data.
- Switching the active component pointer before the new version is fully verified was declined because a failed update would leave the application with no usable tool; activation follows the verified rename and record.
- Re-downloading on rollback was declined because the earlier version is already installed and verified, and a network dependency would make rollback fail exactly when a newer catalog is unusable.
- Running several video downloads concurrently was declined because yt-dlp and ffmpeg are CPU and disk intensive and the delivered progress model has one active video; later confirmations are persisted as queued instead.
- Reusing the HTTP engine's worker pool for video was declined because HTTP segments, part files, and Range recovery do not describe a merge or a single output file, and mixing the two would complicate every claim and count.
- Parsing HLS or DASH and decrypting AES-128 in the application was declined because yt-dlp and ffmpeg already own transport, decryption, and codec handling, and a second implementation would add copyright and DRM risk.
- Adding a global proxy or browser-cookie source was declined for this video decision because it would widen the per-task privacy boundary; a later network and cookie decision adds a global proxy and opt-in browser cookies for HTTP while video cookies stay per-download and a per-video proxy overrides the configured one.
- Persisting the full source URL for restart retry was declined for the same privacy reason; the minimized URL is durable and a query-bearing task must be submitted again.
- Putting target-specific process or executable behavior in the video service was declined because the platform layer is the only place for target branches; the service calls shared guarded-process and preparation interfaces.

## Consequences

Later component work must keep the build-time public key, the signed catalog policy, the separate schema version 1 component database, versioned directories with per-file hashes, update and rollback activation rules, and the resolver checks. A release must publish a catalog signed by the key embedded in that build, and no private key may enter the repository.

Later task work must preserve the task kind, the HTTP-only claim and count queries, the `TASK_KIND_UNSUPPORTED` boundary, the version-3 migration and backup, and the rule that video tasks have no byte segments. Later video work must keep one active video, the queued confirmation behavior, the task-owned temporary directory, the bounded process tree and timeouts, unique output and stored SHA-256, and the typed recovery and control outcomes.

The delivered interface depends on the Components and quality flows, kind-aware list and details, and localized component and video errors. The desktop video flow still starts from a pasted URL, and its page overlay still reports that browser-side video download is not available; the later network and cookie decision adds capture protocol version 2 and an opt-in cookie list without changing that video flow.

Real component installation, update, rollback, tamper and no-key behavior, real video download and merge, local HLS AES-128 playback with the real tools, cancellation, timeout, one-video queue, and Windows x64 checks remain manual acceptance items and are recorded as pending. Automated fixtures and mocks do not replace them, and the phase exit remains blocked. The context indexer discovers only TypeScript modules, so the Rust kernel, video, engine, store, commands, api, engine-harness, kernel-manifest, and video-fixture navigation entries stay hand-maintained.
