# Agent Note: Loopback browser capture and Chromium extension

Status: implemented

English | [中文](2026-11-13-local-api-browser-capture.zh.md)

## Problem

OneGet could download files only after the user copied a URL into the desktop application. A browser user needed a direct path from observed page resources and browser downloads into OneGet without exposing a network service, inventing a second credential system, or letting a web page drive the desktop. The missing decisions were how to pair a Chromium extension safely, how a browser download becomes exactly one desktop task, how a captured resource reaches a download dialog without starting it, where page observation belongs, how much resource data may be retained, and how streaming manifests should appear when downloading them is not yet supported. The desktop shell, download engine, and download interface records establish the process, engine, store, and interface boundaries that this capability extends: the [OneGet desktop shell baseline](2026-11-11-oneget-desktop-shell-baseline.md), the [Download engine and durable task store](2026-11-12-download-engine-task-store.md), and the [Desktop download interface and engine service](2026-11-13-desktop-download-ui.md).

## Decision

The browser boundary is a loopback-only HTTP service on `127.0.0.1:37652`, started with the application and stopped before the engine. It is additive and optional: a busy port or an unreadable pairing database disables browser integration while downloads, tasks, and settings keep working. Health discovery is unauthenticated but requires the exact loopback authority and rejects a present non-extension origin. Write routes require the exact `chrome-extension://` origin, a JSON content type where a body is expected, and a bearer token bound to that origin. The token is read only from the `Authorization` header, the service returns no wildcard CORS header, and body, item, URL, header, protocol, and rate limits are enforced before a task or prefill exists.

Pairing uses a dedicated `pairing.db` rather than the task store. It stores only SHA-256 hashes of codes and tokens plus the exact bound origin, label, and timestamps. An eight-digit code lives for ten minutes, is single-use, and is replaced by a newer code; five failed attempts lock pairing for five minutes. A successful exchange returns a 256-bit token exactly once. Revocation deletes the client, and deleting the pairing database revokes every client without touching tasks, completed files, or settings. Separating the database keeps pairing state out of the task schema, makes revocation a local delete, and lets an unavailable or future pairing schema degrade browser integration without risking download data.

Capture protocol version 1 has two intents. A takeover contains exactly one item, creates exactly one desktop task, and deduplicates by the token-bound browser source identifier so a repeated event, including after a service-worker restart, returns the existing task. The extension sends the capture before it cancels and erases the browser download, so a failed or unreachable desktop leaves the browser download intact. A prefill contains one or more items, creates no task, and stores one bounded pending list in memory. The desktop delivers it through an event plus a fetch-on-open command, defers it while another dialog is open, and drops it on dismissal or restart. Only the URL, filename, referer, MIME type, size, file kind, and the safe `Referer`, `User-Agent`, `Accept`, and `Accept-Language` headers are accepted; cookies, authorization values, arbitrary headers, credentialed URLs, and unsupported kinds are rejected.

The extension separates pure logic from browser runtime. `extension/shared` holds framework-free protocol, classification, manifest recognition, segment filtering, page ownership, bounded storage, settings validation, and bilingual strings, so those rules are unit-testable without a browser. `extension/chromium` holds the MV3 manifest, service worker, isolated content script and overlay, and the MAIN-world observer; `extension/popup` holds the resources, pairing, and settings views. The MAIN-world script must wrap page `fetch`, XHR, and history APIs to see requests that never reach `webRequest`, but it has no extension privileges and only posts URL, MIME type, and size metadata to the isolated content script. The isolated script owns all privileged behavior and the overlay.

Resource data stays bounded and session-only. A per-tab store deduplicates by URL without the fragment, keeps at most 500 entries per tab and 50 tabs, and clears the sending frame on a frame navigation or a subframe SPA route change, the whole tab on a top-frame tab navigation or SPA route change, and the tab on close. The background worker rehydrates a bounded `chrome.storage.session` snapshot after a service-worker restart. The pairing token and settings are the only persistent extension data and live in `chrome.storage.local`. Classification derives a category from the filename extension first and MIME type second. HLS and DASH manifests are listed but never taken over and are never fetched for parsing; `.ts`, `.m4s`, `.m4f`, `.cmfv`, `.cmfa`, `init.mp4`, and media `videoplayback` segment URLs are filtered. Takeover additionally honors enablement, category toggles, exact or subdomain blacklist hosts, incognito and extension-originated downloads, non-HTTP URLs, and a minimum size that does not apply to unknown sizes.

Privacy and the content security policy are part of the decision, not later hardening. The MV3 manifest requests only `webRequest`, `downloads`, `storage`, `tabs`, and `webNavigation`, plus HTTP(S) and loopback host permissions. It requests no cookies, no native messaging, no remote code, and no telemetry. The extension-page CSP is `script-src 'self'`, the build bundles all runtime code, and displayed URLs remove credentials, query, and fragment. The desktop never returns a token from a command and never displays one. The overlay runs only in the top frame, reuses one button, and states that video parsing is not available.

## Alternatives considered

- Binding the browser service to all interfaces or exposing a remote endpoint was declined because the capability is local by definition and a wider bind would create an authentication and attack surface the product does not need.
- Storing bearer tokens or pairing codes in plaintext was declined because a copied database would then grant capture access; a SHA-256 hash supports lookup and revocation while leaving no replayable secret.
- Reusing the task database for pairing was declined because browser pairing has a different lifetime, schema, and failure mode, and a pairing migration should not risk task data.
- Accepting any extension or web origin with a valid token was declined because a stolen token would then work from another client; binding the token to the exact origin keeps the credential and its holder together.
- Capturing cookies or authorization headers to improve compatibility was declined because the desktop already treats those values as secrets and the browser owns their scope and lifetime.
- Auto-starting a prefill download on receipt was declined because the user must choose the destination, filename, and controls; a prefilled dialog keeps the existing confirmation boundary.
- Canceling the browser download before the desktop confirms the task was declined because a capture failure would then lose the file; capture-before-cancel keeps the browser download as the fallback.
- Persisting page resources in `storage.local` or parsing video manifests now was declined because page content is sensitive and video download is a later capability; a session-only bounded list and a disabled manifest action avoid both exposures.

## Consequences

The task store and settings remain schema version 2; pairing has its own version 1 database. Later work must preserve the loopback-only bind, the fixed admission order, hash-only tokens, the exact-origin binding, the one-time code and lockout rules, token-bound duplicate suppression, capture-before-cancel takeover, and the single in-memory prefill. New capture fields or kinds need a protocol change and must keep credential values out of the request and the store. New extension observation must stay in the MAIN-world observer or the isolated forwarding path and must never read response bodies, cookies, or authorization values.

The delivered verification covers Rust API and pairing suites, desktop pairing and prefill component tests, extension unit tests, main and extension Playwright suites, production and test extension builds, and the full frontend and Rust gates. Manual Chrome and Edge pairing, sniffing, manifest filtering, prefill, takeover, unpaired and revoked behavior, and Windows install and launch were not performed and remain pending, so the browser-capture exit stays blocked.

- The context indexer discovers only TypeScript modules, so the Rust `api`, `engine`, `store`, `commands`, and harness navigation entries stay hand-maintained.
- Automated and mock-service results do not replace a real browser or a Windows record; a pending manual item must never be recorded as passed.
- HLS and DASH download, video parsing, Firefox support, cookie access, telemetry, and automatic remote capture remain outside this decision.
